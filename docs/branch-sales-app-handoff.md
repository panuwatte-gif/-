# คู่มือส่งต่อ: แอปเก็บข้อมูลการขาย + ตัดสต๊อก สำหรับสาขา

> **Claude ในแชทใหม่: อ่านไฟล์นี้ให้ครบก่อนทำอะไร**
> เขียนเมื่อ 3 พ.ย. 2026 จากแชทที่ทำแอป ReadyProof (โฟลเดอร์ `readyproof/` ใน repo นี้) เพื่อให้แชทใหม่ไม่ต้องเริ่มจากศูนย์
> ส่วนที่ 1–3 คือสิ่งที่เจ้าของต้องการ ส่วนที่ 4 คือความรู้ทางเทคนิคที่พิสูจน์แล้ว ส่วนที่ 5–7 คือข้อควรระวัง แผน และคำถามที่ยังต้องถาม

---

## 1. เจ้าของร้าน และวิธีทำงานด้วย (บังคับ)

- **ตอบภาษาไทย ไม่ใช้ศัพท์เทคนิค** เจ้าของเขียนโค้ดไม่เป็น แต่เก่งธุรกิจ อาหาร บัญชี และภาษีระดับสูง
- **คำตอบต้องระดับผู้เชี่ยวชาญ** ไม่ต้องสอนพื้นฐาน มองเรื่องเป็นความเสี่ยงและความน่าจะเป็น
  - ห้ามตอบว่า "ทำไม่ได้" แบบตัดจบ ให้ตอบว่า "ทำได้ภายใต้เงื่อนไขอะไรบ้าง"
- **ตรวจก่อนส่งทุกครั้ง** ตัวเลขทุกตัวต้องมาจากข้อมูลจริง และต้องบอกที่มาได้ แยกให้ชัดว่าตัวไหน "อ่านจากข้อมูล" "คำนวณ" หรือ "ตีความเอง"
  - แชทเดิมเคยโดนจับได้ว่านับผิด 3 ตัว เจ้าของจะถามว่า "เอาตัวเลขมาจากไหน"
- **คิดผลกระทบรอบด้าน** ไม่ใช่แค่เรื่องตรงหน้า แก้เฉพาะที่ขอหรือที่เจอ ("อย่าพังกว่าเดิมก็พอ")
- **ออกแบบให้พังยาก แก้ซ้ำได้หลายรอบ และเพิ่มฟังก์ชันได้โดยไม่กระทบส่วนอื่น**
  - แยกเป็นส่วนๆ
  - ค่าที่ต้องปรับเก็บในไฟล์ตั้งค่า
  - งานคำนวณอยู่ในส่วนที่ทดสอบได้ (แบบ `readyproof/core`)
- **ห้ามใส่ในโค้ดหรือแอปเด็ดขาด:** Supabase service role key, LINE channel access token, LINE channel secret, Gemini API key, private API key ทุกชนิด
- **ห้ามให้แอปเปิดสิทธิ์ให้ตัวเอง** (เช่น WRITE_SECURE_SETTINGS เพื่อเปิด Accessibility เอง) เจ้าของปฏิเสธไปแล้ว
- เจ้าของด่าเมื่อทำไม่ดี เป็นเรื่องปกติ ให้แก้งาน ไม่ต้องขอโทษยืดยาว

## 2. แอปใหม่ต้องทำอะไร (สรุปจากคำขอของเจ้าของ)

แอป Android ติดตั้งใน**เครื่องที่สาขาใช้รับออเดอร์ Grab จริง** ทำงานพร้อมกับที่พนักงานใช้งาน มีหน้าที่ดังนี้

1. **ไม่ต้องแคปภาพ delay** เพราะสาขาไม่มีปัญหานี้
2. **เก็บข้อมูลการขายทุกออเดอร์** จากหน้าจอที่พนักงานเปิดดูรายการเพื่อจัดอาหารอยู่แล้ว:
   - ลูกค้าเป็นใคร
   - ซื้ออะไร (รวมตัวเลือกเพิ่ม)
   - ยอดเงิน
   - วันและเวลาที่ซื้อ
3. **วิเคราะห์พฤติกรรมลูกค้า:**
   - ซื้อสัปดาห์ละกี่ครั้ง เดือนละกี่ครั้ง
   - ซื้อวันไหน
   - งบต่อครั้ง
   - ซื้ออะไรประจำ
4. **บันทึกยอดขายรายวัน** ว่าขายอะไรไปเท่าไร
5. **แปลงยอดขายเป็นวัตถุดิบเพื่อตัดสต๊อก** ให้รู้ว่าเหลือเท่าไร และต้องสั่งของหรือยัง
6. **ทำรายงานสรุป**
7. เจ้าของอยากให้ "รับข้อมูลจากเซิร์ฟเวอร์ Grab ตรงๆ" ได้ด้วย ซึ่งทำมาแล้วใน `readyproof-pc/` ดูข้อ 4.1

## 3. ต่างจาก ReadyProof ตรงไหน (สำคัญที่สุด)

ตารางนี้ใช้กับกรณีทำเป็นแอป Android ในเครื่องรับออเดอร์ (ทาง ข ในข้อ 6) ถ้าเลือกต่อยอดโปรแกรมเว็บบนคอมพิวเตอร์ (ทาง ก) จะไม่แตะเครื่องพนักงานเลย

| | ReadyProof (แอปเดิม) | แอปสาขา (แอปใหม่) |
|---|---|---|
| เครื่อง | มือถือแยก 1 เครื่อง ไว้เฝ้า Grab อย่างเดียว | **เครื่องที่พนักงานใช้รับออเดอร์จริง** |
| ควบคุมแอป Grab | แตะแท็บ เลื่อนรายการ และพากลับหน้าพร้อมจัดส่งเอง | **ห้ามแตะ เลื่อน หรือเปลี่ยนหน้าใดๆ** อ่านเฉพาะสิ่งที่พนักงานเปิดอยู่บนจอ |
| ภาพ | แคปหน้าจอเป็นหลักฐาน | **ไม่แคป** อ่านข้อความเท่านั้น |
| สิ่งที่เก็บ | เวลาแต่ละขั้น หลักฐานล่าช้า และหน้าประวัติ | รายการอาหาร ตัวเลือก ราคา ลูกค้า และยอดรวม |
| หน้าต่างอื่นบังจอ | ปิดเองแล้วพากลับ Grab | ไม่ต้องทำอะไร (คนกำลังใช้เครื่องอยู่) |
| ผลลัพธ์ | หลักฐานส่ง Grab + Google Sheet เวลา | ยอดขาย + พฤติกรรมลูกค้า + สต๊อก |

หลักข้อแรกของแอปใหม่: **ห้ามรบกวนพนักงาน** ห้ามเด้งหน้าต่าง ห้ามแตะจอ และห้ามทำให้เครื่องช้า ถ้าอ่านไม่ได้ ให้บันทึกว่าอ่านไม่ได้ ห้ามเดา

## 4. ความรู้ที่พิสูจน์แล้วจาก ReadyProof

### 4.1 แหล่งข้อมูลจาก Grab: ที่มีอยู่แล้ว และที่ตรวจแล้ว

1. **เว็บ Grab Merchant Portal บนคอมพิวเตอร์: มีโปรแกรมทำไว้แล้วที่ `readyproof-pc/`** (Windows สร้างเมื่อ 4 ต.ค. 2026 ในอีกแชท) **เป็นจุดเริ่มที่ดีที่สุดของแอปใหม่**
   - **วิธีทำงาน:** Python + Playwright เปิด Chrome แยกโปรไฟล์ ร้านละหน้าต่าง (กะเพรา / ลูกสาวทำเอง) เจ้าของล็อกอินเองครั้งเดียว แล้วโปรแกรมอ่านหน้า `https://merchant.grab.com/order/<store_id>/ready` และหน้าประวัติ แล้วเปิดหน้ารายละเอียดออเดอร์ในแท็บแยก
   - **อ่านจากหน้าเว็บที่แสดงอยู่ (DOM) เท่านั้น** ไม่ได้เรียก API ลับของ Grab ดู `readyproof-pc/README.md` `grab_worker.py` `grab_worker_fixed.py` `core.py`
   - **ข้อมูลที่ได้ ตรงกับที่แอปใหม่ต้องการเกือบทั้งหมด:**
     - เลขออเดอร์ยาวของ Grab (ไม่ซ้ำ) และเลข GF
     - ชื่อลูกค้าตามที่ Grab แสดง และหมายเหตุลูกค้า
     - รายการอาหาร จำนวน ราคา ตัวเลือกเพิ่ม และยอดรวม
     - สถานะในประวัติ และนาทีล่าช้า
     - เก็บลงฐานข้อมูลในเครื่อง ร้านละไฟล์ (`orders.db`)
   - **ผลใช้งานจริงตามที่เจ้าของบอก (3 พ.ย.):**
     - ใช้แล้วไม่มีปัญหากับ Grab
     - อยู่หน้าเดิมแทบไม่ต้องขยับ
     - **แต่ยังเก็บได้ไม่ครบ**
   - **สาเหตุที่น่าจะเป็น** (ยังไม่ได้พิสูจน์ ให้ตรวจก่อน): ตารางออเดอร์บนเว็บแสดงเฉพาะแถวที่อยู่บนจอ (`grab_worker_fixed.py` เขียนไว้ว่าแถวหายจาก DOM เมื่อเลื่อนผ่าน) และต้องเปิดหน้ารายละเอียดทีละออเดอร์ ถ้าเปิดไม่ทันหรือพลาดก็ขาด
   - **ทางแก้ที่ควรประเมินเป็นอันดับแรก:** ให้โปรแกรมอ่าน "ข้อมูลที่หน้าเว็บได้รับจากเซิร์ฟเวอร์ Grab" ในเบราว์เซอร์ที่ร้านล็อกอินอยู่เอง แทนการอ่านตัวหนังสือบนจอ
     - Playwright ฟังข้อมูลตอบกลับของหน้าเว็บได้ จะได้ทุกออเดอร์ครบในครั้งเดียว ไม่ติดเรื่องแถวหาย
     - เป็นข้อมูลเดียวกับที่ร้านเห็นอยู่แล้ว ไม่แตะแอป Grab บนมือถือ
     - ต้องดูก่อนว่าเว็บส่งข้อมูลรูปแบบไหน
   - **ข้อดีสำหรับสาขา:** ไม่รบกวนเครื่องที่พนักงานใช้รับออเดอร์เลย แต่ต้องมีคอมพิวเตอร์เปิดเว็บค้างไว้ (ต้องถาม)
2. **อ่านจอแอป Grab บน Android ผ่าน Accessibility Service** (วิธีของ ReadyProof)
   - พิสูจน์แล้วว่าอ่านได้: เลข GF ข้อความสถานะบนการ์ด ตัวนับถอยหลัง หน้าประวัติ และยอด Completed/Cancelled
   - แพ็กเกจแอป Grab คือ `com.grab.merchant` ใช้ได้ทั้ง Grab ภาษาไทยและอังกฤษ
   - **ถ้าใช้ในเครื่องรับออเดอร์ของสาขา ต้องอ่านอย่างเดียว** และยังไม่เคยอ่านหน้ารายละเอียดออเดอร์ (ดูข้อ 4.2)
3. **อ่านแจ้งเตือนของแอป Grab บนมือถือ** (NotificationListenerService) ได้เวลาออเดอร์เข้า **ยังไม่ได้ทดสอบ**
4. **รายงานดาวน์โหลดจากเว็บ Grab Merchant: เจ้าของตรวจแล้ว ใช้ไม่ได้** ไม่มีข้อมูลที่ต้องการ (เหตุผลที่ต้องเขียนโปรแกรม)
5. **POS ที่เชื่อมกับ Grab อย่างเป็นทางการ** เป็นทางที่ได้ข้อมูลแบบระบบต่อระบบ ต้องดูว่ามี POS ที่ร้านใช้ได้หรือไม่
- **ไม่แนะนำ:** ดักทราฟฟิกที่เข้ารหัสของแอป Grab บนมือถือ (ติดตั้งใบรับรองในเครื่อง) แอป Grab มักป้องกันไว้ และเสี่ยงต่อบัญชีร้านมากกว่าทาง 1–2 ซึ่งได้ข้อมูลเดียวกัน

### 4.2 การอ่านจอ Grab Merchant (ดูโค้ดจริงใน `readyproof/`)

- **ไฟล์ที่ควรดู:**
  - `app/.../ScreenReader.kt`: อ่านโครงหน้าจอ
  - `app/.../NodeSnapshot.kt`: เก็บต้นไม้ข้อความของจอ
  - `core/.../GfExtractor.kt` `ScreenAnalyzer.kt` `CardFinder.kt` `TextNorm.kt` และ `Rules.kt` (มี `Parsers`): แยกเลข GF เวลา และนาทีออกจากข้อความบนจอ
  - `core/.../Config.kt`: ข้อความป้ายทุกตัวทั้งไทยและอังกฤษ เก็บเป็นการตั้งค่า เช่น `readyTabLabels` `preparingTabLabels` `historyTabLabels` `ordersNavLabels` `searchingAny` `driverFoundAny` `arrivedAny` `completedLabels` `delayAny`
- **ข้อความที่พบบนจอจริง:**
  - การ์ดพร้อมจัดส่ง: "กำลังค้นหาคนขับ..." "คนขับจะมารับใน N นาที" "คนขับของคุณมาถึงแล้ว"
  - หน้าประวัติ: "เสร็จสมบูรณ์เมื่อ 12:56 PM" "ล่าช้าไป 4 นาที"
  - เลขออเดอร์บางตัวมีตัวอักษรท้าย เช่น `GF-864F`
- **ยังไม่เคยอ่าน: หน้ารายละเอียดออเดอร์** (รายการอาหาร ตัวเลือกเพิ่ม ราคา ชื่อลูกค้า หมายเหตุ) เพราะ ReadyProof ห้ามแตะการ์ดออเดอร์ จึงไม่รู้ว่าหน้านั้นอ่านเป็นข้อความได้ครบหรือไม่ **ขั้นแรกของแอปใหม่ต้องเก็บตัวอย่างจอจริงก่อน** (ดูข้อ 6)
- การอ่านจอแบบ Accessibility อ่านได้เฉพาะสิ่งที่อยู่บนจอ รายการยาวที่พนักงานไม่ได้เลื่อนดูจะอ่านไม่ครบ ต้องออกแบบให้รู้ตัวว่าอ่านไม่ครบ และนับเทียบกับยอดของ Grab

### 4.3 การเก็บข้อมูลและส่งออก (ใช้ซ้ำได้)

- **เก็บในเครื่องก่อนเสมอ**
  - ไฟล์บันทึกรายวัน เขียนแบบไม่พังกลางทาง (AtomicFile)
  - แอปไม่ลบข้อมูลเอง
  - Drive และชีตเป็นส่วนเสริมที่ทำเบื้องหลัง เน็ตหลุดก็ต้องไม่กระทบการเก็บข้อมูล
- **Google Drive:**
  - ใช้บัญชี Google ของเครื่องผ่าน Google Identity (AuthorizationClient) ขอสิทธิ์ drive และเรียก Drive v3 ตรงๆ ดู `DriveApi.kt` `DriveWorker.kt` `DriveSync.kt`
  - โปรเจกต์ Google Cloud ของเจ้าของเปิดไว้เฉพาะ **Drive API** (ไม่มี Sheets API)
- **Google Sheet:**
  - เขียนไฟล์ .xlsx เองโดยไม่ใช้ library (`core/.../Xlsx.kt`) แล้วอัปโหลดทับไฟล์ Google Sheet เดิมผ่าน Drive ลิงก์และสิทธิ์แชร์คงเดิม ดู `SheetSync.kt` และ `core/.../OrderSheet.kt` (หน้าสรุป ค่าเฉลี่ยตามช่วงเวลา และตารางรายวัน)
  - ไฟล์ .xlsx ทดสอบแปลงเป็นชีตผ่านแล้ว แต่ขั้นเขียนทับจากมือถือเริ่มใช้ใน ReadyProof 1.0.201/1.0.204 และกำลังรอผลจริงคืน 3–4 พ.ย. 2026 **ให้เช็กผลก่อนลอกไปใช้**
- **ถ้าจะใช้ Supabase:** ในแอปใช้ได้เฉพาะ anon/publishable key ร่วมกับ RLS ห้ามใช้ service role key ในแอปเด็ดขาด

### 4.4 การ build และปล่อยแอป

- Repo คือ `panuwatte-gif/-` โปรเจกต์อื่นในนี้คือ `readyproof/` (ห้ามแก้จากแชทใหม่) `readyproof-clean/` และ `readyproof-pc/`
- **โครงสร้าง ReadyProof:**
  - `core`: Kotlin ล้วน ทดสอบในเครื่องได้
  - `app`: Android, minSdk 30, targetSdk 34, compileSdk 35, Java 17
- **ใน cloud container ของ Claude build แอป Android ไม่ได้** (dl.google.com ถูกบล็อก)
  - ทดสอบ `core` ได้โดยสร้าง Gradle project ชั่วคราวที่ชี้ไปโฟลเดอร์ core (Maven Central บางครั้งตอบ 429 ให้ลองใหม่)
  - ส่วนแอปให้ GitHub Actions build
- **CI แยกตามโฟลเดอร์** (paths filter) ดูตัวอย่างที่ `.github/workflows/readyproof-android.yml`
  - ขั้นตอนใน workflow: ทดสอบ → assembleRelease → เซ็น → ปล่อย release แท็ก `readyproof-latest` (ลิงก์ APK คงที่) โดยเลขเวอร์ชันคือเลข build ของ CI
  - **แอปใหม่ต้องมีของตัวเองทั้งหมด:** โฟลเดอร์ใหม่ workflow ใหม่ applicationId ใหม่ ชื่อ release tag ใหม่ และ keystore ใหม่ (ReadyProof ใช้ `readyproof/keystore/readyproof.p12`) ห้ามใช้ applicationId ซ้ำ เพราะจะติดตั้งทับ ReadyProof
- **ขั้นตอนทำงานที่ใช้อยู่:**
  1. แตก branch แล้ว commit
  2. เปิด PR
  3. รอ CI ให้ build ผ่าน
  4. merge
  5. เช็กว่า release ออก
  6. ส่งลิงก์ APK ให้เจ้าของ
- เช็ก "Workers Builds: app-recipe" (Cloudflare) จะแดงบน PR เสมอ เป็นของโปรเจกต์อื่น ไม่เกี่ยวกับงานนี้

## 5. ข้อควรระวังเชิงธุรกิจและข้อมูล (บอกเจ้าของตั้งแต่ต้น)

- **ตัวตนลูกค้าไม่แน่นอน 100%**
  - Grab แสดงแค่ชื่อที่ลูกค้าตั้ง ไม่มีเบอร์หรือรหัสลูกค้าถาวรให้ร้านเห็น
  - "ลูกค้าคนเดิม" จึงต้องเดาจากชื่อ ประกอบกับข้อมูลอื่นที่จออาจมี เช่นหมายเหตุ หรือรูปแบบการสั่ง
  - รายงานความถี่ต่อลูกค้าต้องบอกระดับความมั่นใจ และชื่อซ้ำกันได้
- **ข้อมูลส่วนบุคคล (PDPA) และข้อตกลง Grab**
  - ข้อมูลลูกค้าที่ Grab ให้ร้าน มีไว้เพื่อทำออเดอร์ การเก็บไว้วิเคราะห์ถือเป็นข้อมูลส่วนบุคคล
  - **เจ้าของตัดสินใจแล้ว (3 พ.ย.): เก็บชื่อจริงได้** ("ได้หมด") เจ้าของรับทราบความเสี่ยงแล้ว ไม่ต้องถามซ้ำ
  - ให้เก็บเฉพาะในระบบของร้าน และจำกัดคนที่เข้าถึงได้
- **ตัดสต๊อกจากยอด Grab อย่างเดียวจะคลาด** ถ้าสาขาขายช่องทางอื่นด้วย เช่นหน้าร้าน LINE MAN ShopeeFood หรือ Robinhood ต้องรู้ทุกช่องทางและวิธีนำยอดเข้า
- **สูตรตัดวัตถุดิบ** (เจ้าของเชี่ยวชาญเรื่องนี้ ให้ถามรายละเอียด อย่าสอน):
  - เมนู → วัตถุดิบ × ปริมาณ
  - ตัวเลือกเพิ่มหรือลด เช่น ไข่ดาว พิเศษ ไม่ใส่ผัก
  - หน่วยซื้อกับหน่วยใช้ต่างกัน
  - % สูญเสีย
  - นับสต๊อกจริงเป็นระยะ เพื่อเทียบกับยอดที่ควรเหลือ
  - จุดสั่งซื้อ = ใช้เฉลี่ยต่อวัน × วันรอของ + ของกันขาด
- **ชื่อเมนูในแอป Grab** ต้องมีตารางจับคู่ "ชื่อในแอป ↔ สูตร" ที่เจ้าของแก้เองได้ (เช่นใน Google Sheet) เพราะชื่อเมนูและตัวเลือกเปลี่ยนได้ตลอด ห้ามฝังไว้ในโค้ด

## 6. แผนที่แนะนำ (ยืนยันกับเจ้าของก่อนลงมือ)

0. **ถามคำถามในข้อ 7 ก่อนเขียนโค้ด** แล้วเลือกฐานของแอปใหม่
   - **ทาง ก:** ต่อยอด `readyproof-pc` (เว็บบนคอมพิวเตอร์) แนะนำถ้าสาขามีคอมพิวเตอร์ เพราะได้รายการอาหารและลูกค้าแล้ว และไม่แตะเครื่องพนักงาน
   - **ทาง ข:** แอป Android อ่านจอในเครื่องรับออเดอร์
   - ถ้าเลือกทาง ก ให้เริ่มจากหาว่า `readyproof-pc` เก็บไม่ครบตรงไหน แล้วลองอ่านข้อมูลที่หน้าเว็บได้รับ (ข้อ 4.1) ก่อนทำส่วนอื่น
   - **ลอกเป็นโฟลเดอร์ใหม่ ห้ามแก้ `readyproof-pc/` ตัวเดิม** เพราะร้านอาจยังใช้อยู่
1. **(ทาง ข) เก็บตัวอย่างจอจริง 1–2 วัน**
   - แอปอ่านอย่างเดียว บันทึกข้อความบนจอทุกหน้าที่พนักงานเปิดในแอป Grab
   - ไม่แคปภาพ ไม่แตะจอ
   - เป้าหมาย: รู้ว่าหน้ารายละเอียดออเดอร์และแจ้งเตือนให้ข้อมูลอะไรบ้าง ก่อนออกแบบการแยกข้อมูล
2. **แยกออเดอร์ออกเป็นรายการ**
   - ได้: เลข GF เวลา รายการอาหาร ตัวเลือก จำนวน ราคา ยอดรวม และลูกค้า
   - บันทึกรายวัน
   - ทุกวันต้องเทียบกับยอดของ Grab เอง แล้วบอกว่าอ่านครบกี่ออเดอร์
3. **ตัดสต๊อก**
   - ใช้ตารางสูตรที่เจ้าของแก้ใน Google Sheet
   - แปลงยอดขายเป็นวัตถุดิบที่ใช้ แล้วคำนวณสต๊อกคงเหลือ
   - เตือนเมื่อถึงจุดสั่งซื้อ
   - มีช่องให้บันทึกของเข้าและผลนับสต๊อกจริง
4. **รายงาน**
   - ยอดขายรายวัน รายเมนู และรายช่วงเวลา
   - พฤติกรรมลูกค้า: ความถี่ต่อสัปดาห์และต่อเดือน วันที่ซื้อ ยอดต่อครั้ง เมนูประจำ
   - สต๊อกและรายการที่ต้องสั่ง
   - ปลายทางรายงานตามที่เจ้าของเลือก
- **ของที่ลอกจาก ReadyProof ได้เลย** (ลอกเป็นไฟล์ใหม่ในโฟลเดอร์แอปใหม่ ห้ามแก้ของเดิม):
  - `Xlsx.kt`
  - รูปแบบหน้าสรุปใน `OrderSheet.kt`
  - `DriveApi.kt` `DriveWorker.kt` `SheetSync.kt`
  - รูปแบบไฟล์ตั้งค่า `Config.kt`
  - การเก็บบันทึก `RecordStore.kt`
  - workflow ของ CI

## 7. คำถามที่ต้องถามเจ้าของ (ยังไม่มีคำตอบ)

1. สาขาไหน ใช้บัญชีร้านใน Grab ชื่ออะไร แยกจากร้านกะเพราหรือไม่ และมีกี่สาขาที่จะใช้
2. เครื่องรับออเดอร์ของสาขาเป็นรุ่นอะไร (Sunmi หรือมือถือ) Android เวอร์ชันไหน และพนักงานใช้แอปอะไรในเครื่องนั้นบ้าง โดยเฉพาะแอปธนาคารหรือแอปรับเงิน
3. พนักงานดูรายการอาหารจากหน้าไหน (หน้ารายละเอียดออเดอร์ในแอป ใบที่พิมพ์ออกมา หรืออย่างอื่น) และเปิดดูทุกออเดอร์หรือไม่
4. สาขาขายช่องทางอื่นนอกจาก Grab ไหม และถ้ามี ยอดขายช่องทางนั้นบันทึกที่ไหน
5. สาขามีคอมพิวเตอร์ (Windows) ที่เปิดเว็บ Grab Merchant ค้างไว้ทั้งวันได้ไหม และ `readyproof-pc` ที่ใช้อยู่เก็บไม่ครบตรงไหน (ขาดทั้งออเดอร์ ขาดรายการอาหาร หรือขาดตัวเลือก) และเกิดช่วงไหน
6. สูตรและวัตถุดิบมีอยู่แล้วหรือยัง อยู่ในรูปแบบไหน และใครดูแล
7. ของเข้าและการนับสต๊อก ใครบันทึก บ่อยแค่ไหน ใช้หน่วยอะไร และผู้ขายส่งของกี่วันถึง
8. อยากดูรายงานที่ไหน (Google Sheet / LINE / หน้าจอในแอป) ใช้บัญชี Google หรือโปรเจกต์ Supabase ไหน
